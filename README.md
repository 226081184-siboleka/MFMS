. Problem Description
A municipality must keep track of its staff and their pay, departmental budgets and spending, suppliers, and physical assets. Managing this by hand makes it difficult to search records, calculate figures consistently, and see which departments have overspent. The group was asked to build a first, working console application that captures this information, validates it, allows searching, performs the calculations, and produces summary reports.
3. System Objectives
•	Provide a clear, menu-driven C application with navigation between modules.
•	Store and process records using arrays and strings.
•	Accept and validate user input (for example, rejecting negative amounts and empty names).
•	Calculate employee salaries and remaining department budgets, and identify departments over budget.
•	Search employee, supplier and asset records.
•	Produce employee, budget, supplier and asset reports.
•	Organise the program into functions and separate modules, and collaborate through Git and GitHub.
4. System Features
Main menu (main.c). Six options (Employee, Budget, Supplier, Asset, Report, Exit) handled with a while loop and a switch. Non-numeric input and out-of-range numbers produce an error message and the menu is shown again.
Employee Management (employees.c/.h, input.c/.h). Add, display, search, salary breakdown and employee report. Each employee stores ID, name, department, email, level, basic salary, housing allowance, transport allowance and tax. Gross salary = basic + housing + transport; net salary = gross − tax. IDs must be non-empty and unique, names must be non-empty, all amounts must be non-negative, and tax may not exceed gross salary. Search matches an ID or an exact name. The report shows total employees, average basic salary, average housing and transport allowance, and highest and lowest basic salary.
Budget Management (budget.c/.h). Add a department budget, record expenditure (added to the running total), display budget information, and list departments over budget. For each department the system shows allocated budget, expenditure, remaining budget, and a status of WITHIN BUDGET or OVER BUDGET. Department names are trimmed, must be non-empty, and must be unique; an allocated budget must be greater than zero and expenditure may not be negative.
Supplier Management (suppliers.c/.h). Add, display, search and compare suppliers (ID, name, email, phone, town). The ID must be a positive, unique integer; name, email and town must be non-empty and the email must contain @. Search is by ID or by name (partial match using strstr). The compare function displays two suppliers side by side and uses strcmp to report whether names, towns and emails are identical.
Asset Management (assets.c/.h). Add, display and search assets (ID, name, type, purchase value, department, condition) and an asset report. Asset IDs are converted to upper case, may not contain spaces and must be unique. Type (Vehicle, Computer, Building, Equipment, Office Furniture, Other) and condition (Excellent, Good, Fair, Poor) are chosen from menus, and purchase value must be greater than zero. Search works by ID, name, type or department (case-insensitive). The report shows the asset table, total count, total value and number of assets in poor condition.
Reports (reports.c/.h). A reports menu with Employee, Budget, Supplier and Asset reports. The Budget report shows number of departments, total allocated budget, total expenditure, remaining budget and departments over budget. The Employee report prints the employee statistics from the Employee module, the Supplier report lists all registered suppliers with a total, and the Asset report calls the asset module’s report.
5. Program Design
Modular structure. The program is split into one source/header pair per module: employees, budget, suppliers, assets, reports, plus input (shared input helpers) and main.c, which contains only the main menu. A test_suppliers.c file runs the supplier module on its own for testing. Each module exposes a menu function (EmployeeMenu, BudgetMenu, SupplierMenu, AssetMenu, ReportsMenu) which main() calls from a switch statement.
Data storage. Data is held in memory in arrays and is not saved to disk. The modules use two approaches:
Module	Storage	Capacity
Employees	Array of Employee structures	100
Budget	Parallel arrays (names, allocated, expenditure)	20 departments
Suppliers	Parallel arrays (ID, name, email, phone, town)	100
Assets	Parallel arrays (ID, name, type, value, department, condition)	100
Functions and parameters. Calculation functions use pass-by-value and return results, for example calculateRemaining(double allocated, double spent) and isWithinBudget(double allocated, double spent). calculateSalary(const Employee *e, float *gross, float *net) passes the employee by pointer and returns the gross and net salary through output parameters. The Budget, Supplier and Asset modules also provide getter functions (such as getTotalAllocated(), getSupplierCount(), getTotalAssetValue()) so the Reports module can read their data without keeping any data of its own.
String handling. strcmp() is used for ID and name matching (employees, assets, budget departments) and for supplier comparison; strlen() detects empty input; strcpy() stores validated text into the arrays; strstr() performs partial supplier-name search; strchr() checks for @ in supplier emails; strcspn() removes the newline from fgets() input.
Input validation. Shared helpers in input.c – readLine(), readNonNegativeFloat() and readIntInRange() – read input with fgets(), convert it with strtof()/strtol(), and repeat the prompt until the value is valid. The Budget and Asset modules contain their own equivalent helpers (readAmount, readPositiveDouble, readIntInRange).
6. Challenges Encountered
We met the following challenges while building and integrating the system:
•	Integrating modules written separately. Each member developed a module independently, so function names and calls had to be matched to main.c. The assets.c/assets.h code had to be moved from outside the main branch into it, and budget.c/budget.h had to be edited to match the calls in main.c.
•	Compilation errors during integration. The first combined version did not compile. main.c had a stray \ in a printf, a missing semicolon, a misspelled variable (Choice/choice) and a missing closing brace; employees.h had an extra #endif; assets.c had an extra closing brace; and EmployeeMenu() was declared in employees.h but never defined in employees.c.
•	Dependent modules. The Reports module depends on the other modules. The Employee and Supplier reports in reports.c were placeholders while those modules were being finished.
•	Input handling. Some input loops repeated forever in two situations: when a letter was typed at the supplier menu, and when input ended (Ctrl+D or Ctrl+Z) in the middle of a prompt. In addition, modules used different input methods (scanf in the Supplier and Reports menus; fgets-based helpers elsewhere), and several modules define their own helper functions, which duplicates code.
•	Team coordination. Seven members worked on one repository using branches (the repository shows 5 branches and 109 commits), so changes had to be reviewed and merged into main without breaking other members’ modules.
7. Solutions Implemented
•	Module interfaces were defined in header files, and main.c calls one menu function per module.
•	All compile errors listed in Section 6 were corrected. EmployeeMenu() was written in employees.c with its own employee array, and the project now builds with gcc -std=c99 -Wall -Wextra with no errors or warnings.
•	The Reports module was connected to real data. showEmployeeReport() in the Employee module prints the employee statistics, and the Supplier report uses displaySuppliers() and getSupplierCount().
•	Shared input helpers (input.c/.h) validate numbers and text in one place. The supplier menu now rejects non-numeric input, and every input loop now exits cleanly when input ends instead of repeating forever.
•	Getter functions in the Budget, Supplier and Asset modules let the Reports module read totals and records without duplicating data.
•	Testing. We wrote a script (run_tests.sh) that runs the built program with typed input and checks the output. It contains 41 tests covering the main menu, employees, budget, suppliers, assets and reports, including negative salary, empty names, duplicate IDs, tax above gross salary, over-budget status, an email without @, search by ID, name and type, and the connected reports. All 41 pass. A separate build with AddressSanitizer and UndefinedBehaviorSanitizer reported no errors. test_suppliers.c runs the supplier module on its own so it can be tested by hand.
•	Work was divided by module and merged into the main branch through pull requests, which the Student 6 role reviewed and approved (for example, the supplier module).
8. Conclusion
The MFMS foundation system provides a menu-driven structure covering employees, budgets, suppliers, assets and reports, built from separate C modules that use arrays, strings, loops, decisions, functions and input validation. The final program compiles as a single project, all four reports work, and invalid input is rejected throughout. Known limitations are that data is held in memory only and is lost when the program exits, and that some modules still use their own input helpers or scanf. In Project B we plan to replace these with the shared input.c helpers and to add saving data to files, building on this foundation.
